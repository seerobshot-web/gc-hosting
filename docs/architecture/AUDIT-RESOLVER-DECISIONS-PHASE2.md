## Resolver contract, not implemented

Only a server adapter may invoke the future resolver; it must bind a `RolesGuard`-produced `TenantContext` to the authenticated user for interactive routes, or an approved system principal to a persisted GCH target for jobs. The resolver must validate the **exact approved action–target pair before querying**, perform a unique-by-PK relational lookup with selected tenant key only, and compare all independently available FK-backed organizations. No caller-supplied org ID, metadata, actor string, email, browser field, provider ID, local payment/provisioning flag or arbitrary first match proves scope. Candidate proofs need a binding to the requested target ID and a reviewed trust boundary; the pure PR #64 helper does not authenticate its inputs. Historical deleted targets cannot be reconstructed from current rows.

```ts
// Design sketch only. No executable resolver, production allowlist or principal exists.
type AuditResolution =
  | { state: "resolved"; organizationId: string; proof: "reviewed_fk" }
  | { state: "not_found" | "not_member" | "deleted_target" | "conflict"
      | "unsupported_shape" | "malformed_evidence" | "unavailable"
      | "cross_tenant" };
interface ServerAuditResolutionRequest {
  action: string;
  target: { type: string; id: string };
  principal: "guard_verified_user" | "approved_system_job"; // provenance must be enforced by server, not asserted by caller
}
```

The request sketch is intentionally insufficient to implement: concrete authenticated principal type, deleted-target proof captured before deletion, action allowlist, system-job authorization, transaction/snapshot boundary and query adapter all need review. The `resolved` result alone is assignable *only after* schema, policy and writer approvals. State behavior below is **proposed** and not a change to existing audit writes:

| State | Assign key? | Future normal event write? | Review/retry proposal | Separate safe security event? | Redact in ordinary logs |
| --- | --- | --- | --- | --- | --- |
| resolved | Only after all approvals | Only with authenticated proof and approved writer | No retry | Not needed | Target IDs, actor details, metadata, provider/payment fields |
| not_found | No | No scoped write; current writer behavior unchanged until cutover policy | Manual review of target existence | Only if separately approved | Queried ID and SQL errors |
| not_member | No | No scoped write | Security deny, no fallback to another org | Only aggregate reason if approved | User/org IDs and existence hints |
| deleted_target | No | No inferred scope; separately approve pre-delete proof | Hold historical row for review | Only if approved | Deleted target and prior payload |
| conflict | No | No scoped write | Quarantine conceptually; operator decision, no first match | Aggregate safe code if approved | Competing org IDs/evidence |
| unsupported_shape | No | No scoped write | Await approved action–target pair | Aggregate safe code if approved | Raw action/payload if user-controlled |
| malformed_evidence | No | No scoped write | Hold and review | Aggregate safe code if approved | Evidence and exception text |
| unavailable | No | No newly inferred key | Proposed bounded retry after availability; timing/attempt policy unapproved | Aggregate outage counter if approved | Connection strings, stack secrets, target IDs |
| cross_tenant | No | No scoped write | Deny; no target-existence disclosure | Aggregate safe security event if approved | Requested/actual tenant and target IDs |

Never make a security event recursively depend on the rejected audit writer. Existing writes remain intact until a separately approved behavioral cutover defines whether to defer, quarantine or reject a normal event for each producer.

## Migration alternatives and query decision

`AuditLog.orgId → Org.id` is a **candidate nullable key**, not an approved FK or migration. `ON DELETE RESTRICT` may preserve attributable audit ownership but can prevent deleting an Org; `ON DELETE SET NULL` may permit deletion but loses tenant attribution and would make previously scoped history inaccessible. `ON DELETE CASCADE` would remove audit content and is incompatible with preservation; do not select it. No existing migration selects the correct audit retention policy. Target deletion (Order, Membership, DomainVerification etc.) is distinct from Org deletion because the audit FK would point to Org. Restoration, archival and rollback when keys are populated remain open. Old rows stay null; changing to required is a later separately approved policy.

Proposed future read for review **only**: require guard-verified tenant and query `WHERE orgId = authorizedOrgId` and `orgId IS NOT NULL`; order `createdAt DESC, id DESC`, use a bound on rows and a compound cursor predicate on `(createdAt,id)`; project only approved redacted fields, never raw metadata by default. Candidate supporting index `(orgId, createdAt, id)` requires approved query semantics and representative MySQL EXPLAIN/size/selectivity evidence. No tenant-scoped reads are presently executed, so index and pagination are **pending**, not decided. MySQL version, DDL lock strategy, table size, index build duration, backup/restore proof, approved migration window and owners are absent from inspected evidence. DDL rollback after new writes is not equivalent to dropping a column; preserve original content and scope keys through an approved forward repair.
