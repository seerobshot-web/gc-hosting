## Proposed resolver contract and trust boundary

`apps/api/src/audit/audit-resolver.proposed.ts` exports **types only**, no minting factory or runtime code. Opaque TypeScript brands distinguish proposed server-bound target, verified principal and exact approved pair. A type assertion can bypass them: only future runtime code owned by security may authenticate guard-provided identity, system-job authority, and a GCH PK lookup. The API must never accept caller-supplied tenant assignment or a relation-candidate array. Match pair.targetType to target.targetType at runtime, bind query to targetId PK, select only verified FK paths, check all independent paths and hold `0` or conflicting results. Identity from actor, metadata, browser values, provider IDs and local paid/provisioning flags is forbidden. System jobs need their own reviewed principal contract; `TenantContext` is not available to all producers.

| Resolution | Assign orgId? | Proposed write/review behavior (not implemented) |
| --- | --- | --- |
| `resolved` | Only after approvals and nullable schema | Reviewed writer may persist scoped event with server-bound PK proof. |
| `not_found`, `deleted_target` | No | Hold for event-specific historical/deletion policy; never infer owner. |
| `not_member`, `cross_tenant` | No | Deny without exposing whether target exists; separate safe aggregate event only after approval. |
| `conflict` | No | Manual review; no arbitrary first match or duplicate provider/user lookup. |
| `unsupported_shape`, `malformed_evidence` | No | Safe reason code only, hold/deny under approved writer contract. |
| `unavailable` | No | Candidate for bounded retry; number/timing/idempotency not approved. |

Existing writes remain intact until explicit cutover approval; this is a proposed future behavior, not current code. Logs must omit target/user/order/provider/payment IDs, competing orgs, credentials, metadata and raw exception text. No new route or audit-row read is added.

## Migration decision record (no migration)

`AuditLog.orgId → Org.id` is a candidate nullable relationship. `RESTRICT` preserves attribution but could prevent deletion of an organization. `SET NULL` permits deletion but erases the tenant key needed to read past audit history. `CASCADE` could delete audit content and conflicts with preservation. **No action is selected** absent a named retention/schema owner. A deleted target such as Membership is a separate case from deletion of Org. A later required column needs a separate policy for orphaned legacy rows.

A future query candidate is `WHERE orgId = authorizedOrgId` with approved redacted projection, bounded page size and keyset ordering `createdAt DESC, id DESC`; `(orgId, createdAt, id)` is only a candidate index. Null rows remain inaccessible. Query shape, cursor encoding/validation, selectivity, MySQL EXPLAIN, version, table size, DDL lock cost and backup/recovery evidence are unapproved. No Prisma schema/migration change is allowed. Rollback after populated keys cannot safely assume a DROP COLUMN; approve forward repair and preserve original audit fields.

## Security and validation boundary

High severity if future code trusts branded types without runtime proof: TypeScript assertions can forge them; require server-only runtime factories and PK-bound read port plus exact allowlist. Cross-tenant IDOR prevention still relies on guard and fail-closed 503. Future resolution must avoid dynamic SQL identifiers, unbounded queries, raw audit metadata rendering, SSRF via configured URLs, unsafe redirects, token replay and sensitive logs. This phase changes no browser bundles, source maps, HTML, analytics, client env vars, dependencies, lockfile, route, SQL, CORS, CSRF surface, secrets or provider calls. Review JWT and integrity worker separately.

**Side effects:** none on providers, Stripe, Hostinger, ResellPortal, payment, database, audit-row write/read, deployment, fulfillment, provisioning or entitlement. No production, staging, shared or disposable DB was accessed.
